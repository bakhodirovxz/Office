# Desktop host (WP9)

`services/suite-desktop` builds `suite.exe` (no console window). It starts `suite-serve` in-process on `127.0.0.1:<free port>` and shows the shell in a WebView2 window (wry 0.57, tao 0.37, rfd 0.17: MIT/Apache; all Windows-only in `Cargo.toml`).

- Command line: `suite.exe [--dist D] [--shell D] [--brand F] [--bin-dir D] [--browser] [--history FILE] [--] [FILE...]`. A file opens in its editor exe (`brand.toml` `bin`, extension table of PLAN 7.2) found in `--bin-dir` (default: next to `suite.exe`).
- IPC (`window.ipc.postMessage(JSON)`, only from `http://127.0.0.1:<port>`, 8 KiB max, exact fields, anything else is refused): `open{path}`, `pick{app?}`, `recent{}`, `history{}`, `settings_get{}`, `settings_set{key,value}` (`lang`, `toolbar`, `latin_alphabet` and `theme` only, each value checked by `suite-core`; see `shared-services.md`). Replies arrive as the `suite-host` DOM event. Paths from the page: absolute, drive-letter only (no UNC), no `..`, known extension, existing file. Navigation is limited to our origin, new windows are denied, devtools are off.
- Local access key (review M1): `suite.exe` makes a 256-bit key per launch (never written to disk, not in `host.json`) and gives it to `suite-serve` (`Layout.local_key`). `GET /_k/<key>` answers 303 to `/` and sets `k=<key>; Path=/; HttpOnly; SameSite=Strict`; every other request without that cookie gets 403, so another local user who finds the port gets nothing. The WebView and the browser fallback open `http://127.0.0.1:<port>/_k/<key>` (the fallback dialog shows the URL without the key). Plain `suite-serve` (web host) has no key and is unchanged. Tests: `suite-serve/tests/serve.rs` `desktop_key_gates_every_request`, `suite-desktop/tests/host.rs`.
- Storage (review M2): the WebView runs InPrivate and its old profile folder is deleted at every start. Recent comes from the host (`recent` IPC: every open, and every download recorded by the host's download handler), the language from `settings_get`/`settings_set`. A download (an editor's Save) is accepted only for our file types, goes to the default downloads folder under a name that is not taken, and is reported to the shell as `saved`. There is no native Save dialog yet. In the browser fallback and when connected to a server the shell keeps file names only (in the tab; cleared on Disconnect).
- WebView2 settings (review m6, m2): browser accelerator keys and the default context menu are off, so WebView2's own Print and "Save as" cannot make a copy without the editor's watermark or bypass our UI; the editors' own print and export commands are unaffected. SmartScreen stays off (wry's default, decision 2026-10-22): the WebView loads no remote content and its downloads are the user's own documents made from our origin (`blob:`); SmartScreen would send their names or hashes to Microsoft, which is a privacy problem for HR files. New windows are denied, devtools are off, top-level navigation stays on our origin (`blob:` of our origin is still allowed: whether a download link needs it is not verified).
- Editors inside the window (checked 2026-10-22 with `scripts/desktop-editors-check.mjs`, which drives the real `suite.exe` over the WebView2 debugging port): with accelerator keys off, Ctrl+P still reaches the editors' own print UI (Docs, Sheets, Slides: the canvas changes, no browser window opens), Ctrl+S in Docs and Sheets saves one file through the download handler, and Ctrl+Plus, Ctrl+Minus, Ctrl+0 and Ctrl+wheel leave the page zoom alone (they are the editors' own shortcuts: in Sheets Ctrl+Minus opens Delete cells). Slides has no host bridge yet (PLAN F7), so Ctrl+S there is not checked. The editors print through their own egui command, and a hidden-iframe `print()` of a PDF for the final dialog; neither needs a browser accelerator. Manual check still worth doing once on a real desktop: finish a print from the editor's print UI to the system printer or PDF, because the script stops at the editor's own print screen.
- Paths (review m1, m12): `open` from the page works only for a path already in `history.json`. Every source refuses `:` after the prefix (ADS) and DOS device names; the page also refuses a path whose canonical form is a network share. `brand.toml` `bin` must be `[A-Za-z0-9._-]+` and start with a letter or digit. Editors start with the install folder as current directory, and `suite.exe` restricts later DLL loads to the application folder and System32.
- Single instance (F14, review B1): the first `suite.exe` owns the named pipe `\.\pipe\<product.id>-host-<user SID>-<session id>` (`first_pipe_instance`, local clients only). Every instance is created with the protected DACL `D:P(A;;GA;;;<own SID>)`, so no other user can connect. A second launch opens the pipe with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` (the server cannot impersonate us), checks that the server process runs as our SID (`GetNamedPipeServerProcessId`, then the process token's user) and only then sends `open`/`focus` lines and exits 0. If the check fails, or nobody answers, nothing is sent and the files open stand-alone.
- Unsafe code: the workspace forbids it. The Win32 calls that need it (user SID, pipe server identity, the DACL, `SetDefaultDllDirectories`) are in `services/suite-winsec`, one `sys.rs` module with a SAFETY comment on each block; the crate's lint is `deny` with a single module-level `allow`. `suite-desktop` itself stays `forbid`.
- No WebView2 (or `--browser`, or `SUITE_FORCE_NO_WEBVIEW2=1`): the default browser opens the local URL and a dialog says so; the server lives while the dialog is open. Dialog text is English only (not yet in the i18n catalogs).
- Test hooks (env): `SUITE_DATA_DIR`, `SUITE_INSTANCE`, `SUITE_BROWSER`, `SUITE_FORCE_NO_WEBVIEW2`, `SUITE_TEST_EXIT_AFTER_MS`. They exist in debug builds only (`cfg(debug_assertions)`); a release binary ignores them (review m10), so `scripts/smoke-desktop.ps1` and `tests/host.rs` need a debug `suite.exe`.
- windows-gnu imports `WebView2Loader.dll`: ship it next to `suite.exe`. The msvc build links it statically. Data: `%LOCALAPPDATA%\<product>\Host` (history.json, host.json, webview2/). The settings are the shared `%APPDATA%\<product>\settings.toml` that the apps read too (`suite-core`, WP5); the old `settings.json` is no longer read.
- Smoke: `scripts/smoke-desktop.ps1` (release, this PC, WebView2 155): window in about 1.9 s, server about 1.4 s, host 28 MB, WebView2 6 processes about 285 MB, second launch handed to the running instance.
- History (WP10, `suite_core::history`, the store under `%LOCALAPPDATA%\<product>\history`). The page sees only documents that have versions; the host's open log (`history.json`) stays internal as the whitelist of `open` and Recent. IPC, all exact-field and 8 KiB like the rest:
  - `history{}` -> `{type:"history", items:[{path, app, versions, ts, size}]}` (`ts` = last version, seconds; `path` is the canonical store path, usually with the `\?\` prefix).
  - `history_versions{path}` -> `{type:"history_versions", ok, path, items:[{v, parent, sha256, size, time, author, message, name, restored_from}], verified, problem}` (`verified` = `Store::verify`: the chain and every live version's bytes).
  - `history_view{path, v}` -> `history_view{ok, v, name, copy:true}`: the version's bytes are written to `<host data>	emp
ame (v3 view).ext` (a free name, deleted at the next start; a copy an editor still holds stays) and opened in its editor. Read-only by being a copy: saving it makes a new file, the document and its history are untouched.
  - `history_restore{path, v}` -> `history_restore{ok, version}` (`Store::restore`: the current file is kept as a version first, then the old bytes are written as a NEW version). A locked target gives `ok:false` with the OS error.
  - `history_copy{path, v}` -> `history_copy{ok, v, path}`: into `%USERPROFILE%\Downloads` under a free name `name (v3).ext` (`download_target`).
  - `history_name{path, v, name}` -> `history_name{ok, v}` (empty name clears).
  - A `path` must be the path of a document that has versions (with or without the `\?\` prefix) and pass the page path rules (absolute, drive letter, no UNC, ADS or device name, known extension, file exists); otherwise the reply is `rejected`, like any other refusal. A failed action replies with its own type and `ok:false`.
- `--history FILE` (what an editor's `suite_core::history::open_panel` starts): the first instance starts on `/_k/<key>#history=<urlencoded path>` (the fragment survives the 303), a running instance gets a `{"type":"history","path":...}` line over the pipe (same SID checks as `open`/`focus`) and sends the shell a `show_history{path}` event, which sets `#history=...`. The path is checked as a command-line path (`check_file`, user source); a bad one is shown in a dialog. Navigation stays limited to our origin.
- A download made by an editor in the window (`saved`) also gets a version (`Store::snapshot`, errors ignored), so the web-editors-inside-the-window path has history too. The store is the user's (`Store::from_settings`); the debug data-dir hook keeps it in `<data>\history`.
- The shell's History panel (`web/shell/history.js`, `history.css`, route `#history`, nav entry only when `window.ipc` exists; in the browser or server mode the route only says it needs the desktop app) lists the documents, the versions (number, time, author, name, message, size, short hash, chain verified/damaged) and offers View, Restore (confirm dialog), Save a copy and Name per version. It says that comparing versions arrives in Phase 5. Strings: `hist.*` in `web/shell/i18n.json`, Uzbek marked `draft:agent-sonnet:2026-10-24` under `_drafts`.
- Not done: `GATE-FLOW desktop` (needs the editors' control channels), IPC `new from template`, `search folders`. History, Phase 5: diffs and blame between versions, restoring a file that was deleted from disk (the file must exist now), a server-side store, a rename that keeps the chain (the id is the canonical path, see `history.rs`), the downloads folder from the Windows known-folder API (now `%USERPROFILE%\Downloads`).
