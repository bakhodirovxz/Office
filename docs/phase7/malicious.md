## Findings

1. **R1, not blocked natively (fixed).** `Machine::resume` and `Remote::reads` looped over `next.reads` without a count, and each text map
   read walks the whole document, so one answer with tens of thousands of short entries (the 1 MiB header cap) would have kept the editor
   thread busy. The web page host already capped it at 16. Fix: `Run::read` in `docs-plugins/src/exec.rs` refuses the 17th blob of a
   round (`plugin_api::wire::MAX_BLOBS`, the limit a message has anyway); that covers `next.reads`, `read` actions and the web bridge's
   reads. Test: `more_than_16_reads_in_a_round_are_refused_before_any_is_done`.
2. **M3, plan and code disagreed (aligned).** The PLAN promised `{error: "network not permitted"}` in the next round; the native code
   aborts the invocation (`check_actions` returns `Denied::Network`) and the web host returned the error value. Decision: the code is
   right, a fetch outside the manifest's list is a permission violation like a refused command. `web/plugins/host.js` `checkAnswer` now
   throws and the audit line is `network.refused`; PLAN 5.4 and `docs/plugins.md` say so. A user who declines the web grant dialog still
   gets the recoverable `{error}` (not a violation).

3. **F5 on Android, low UX finding (fixed in the editor layer, p7-gaps).** A second plugin command sent while the first one is pending is refused, the document is not touched and the lock is gone after the first plugin's timeout
   (`F5-busy.json`: the next command works). The refusal text comes from the editor's read-only command gate, "the document is protected (read only)", not the bridge's `plg.busy` ("another plugin is still running"),
   because a palette command meets the gate first; `plg.busy` covers a panel click. Blocked, but the user was told the wrong reason. Fix: `slot_enabled` in `docs-plugins/src/lib.rs` returns `bridge::BUSY` while an invocation is pending, and the engine runs `enabled` before its protection gate, so no upstream patch. Test: `web_bridge::a_palette_command_of_another_plugin_while_one_is_pending_says_busy`. Re-run 2026-11-06 on a docs wasm rebuilt from phase-7 code, in Chromium (`bridge-plugins.spec.ts` F5), in the docserver wrapper and on the emulator (`F5-busy.json`: the status now says "another plugin is still running"): closed.

4. **Plugins page: "did not respond" after a slow file dialog (found 2026-11-06 with the real native dialog, fixed).** `web/plugins/page.js` armed a 20 s
   "the app did not answer" timer for every message to the host, also for `plugins_install`, whose reply waits for the user in the native Open dialog. A user who
   took longer than 20 s (or cancelled after 20 s) saw that error, and a later Cancel left it on the page. Fix: no timer for `plugins_install`
   (`send` in `page.js`). Test: `plugins-page.spec.ts` "a dialog that stays open for more than 20 s does not turn into \"did not respond\"" (fails on the old page.js, passes now).
   The desktop run (`scripts/plugins/desktop-install-check.mjs`, `docs/phase7/evidence/desktop/desktop-install.json`): Cancel gives one `cancelled` reply and no message; Open gives `installed`.
5. **Fixture limit.** A plugin manifest has at most 16 commands (`host.js` and `plugin-api`): the first version of the extended fixture had 20 and was refused at install
   ("20 commands, the limit is 16"). The extra commands are a second plugin (browser specs) or the package `test.recheck` (Android).
