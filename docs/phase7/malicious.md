# Malicious-plugin results (Phase 7 WP10, exit-gate item 2)

Rows are the attacks of PLAN 5.4 (M1 to M12) and the reads cap found in WP10. Each cell names the test that proves the block
(`file::test`), or says `gap`. A blocked attack means: refused, no effect outside the plugin, and the document as it was.
Fixtures are minimal: `ci/plugins/webhost-test/plugin.wasm` (generated by `gen.mjs`: a loop, a memory grower, canned answers) and
the WAT modules inside `crates/plugin-host/tests/host.rs`. They test our own sandbox and nothing else.

## Findings

1. **R1, not blocked natively (fixed).** `Machine::resume` and `Remote::reads` looped over `next.reads` without a count, and each text map
   read walks the whole document, so one answer with tens of thousands of short entries (the 1 MiB header cap) would have kept the editor
   thread busy. The web page host already capped it at 16. Fix: `Run::read` in `docs-plugins/src/exec.rs` refuses the 17th blob of a
   round (`plugin_api::wire::MAX_BLOBS`, the limit a message has anyway); that covers `next.reads`, `read` actions and the web bridge's
   reads. Test: `more_than_16_reads_in_a_round_are_refused_before_any_is_done`.
2. **M3, plan and code disagreed (aligned).** The PLAN promised `{error: "network not permitted"}` in the next round; the native code
   aborts the invocation (`check_actions` returns `Denied::Network`) and the web host returned the error value. Decision: the code is
   right, a fetch outside the manifest's list is a permission violation like a refused command. `web/plugins/host.js` `checkAnswer` now
   throws and the audit line is `network.refused`; PLAN 5.4 and `docs/plugins.md` say so. A user who declines the web grant dialog still
   gets the recoverable `{error}` (not a violation).
