Date 2026-11-01/02, branch `p6-m3`. Plan: `docs/phase6/PLAN.md` section 7. No product code changed.
Fixture: the synthetic `domains/docs/crates/docs-translit/tests/fixtures/uz108-latn.docx` (108 pages in Word, 110 in our layout) and the 1-page

All 12 runs reached `opened`; no renderer death visible (the 0-8 "kill" lines in the logcat excerpts are `Zygote ... signal 9` of the tabs the harness
closes between runs plus lmkd start-up lines; no run lost its page). Wasm memory 161-171 MB for the big file.

What the emulator numbers say:
- `opened` is **not** where the stall shows: the big file is +7 s at 412 dp and about equal at 360 dp versus the control, and the spread of the control
  alone (14-29 s) is larger than that difference. The emulator is slow and noisy for everything (the 1-page file has an 8 s long task too: wasm
  instantiation/first frame under swiftshader), so a 3-run median cannot resolve the document-specific cost from the page-load cost.
- The document-specific cost is the extra long task: longest task 9.5 s (412) / 8.5 s (360) for 108 pages vs 4.3 / 8.3 s for the control (412 dp pair is clean; 360 dp control was inflated by a first-run outlier).
  That puts the layout at roughly 5 s (ESTIMATE, difference of longest tasks, one clean pair) on the emulator.
- Phase 0's 240 s and the 20x-throttle desktop 51 s are not reproduced as one stall. What does occur is a long **tail**: 5 of 6 big runs and also 3 of 6 control runs keep
  producing long tasks (1-2 s each, every few seconds) for 35-220 s after `opened` (`busy_ms_by_10s` stays at 0.5-2 s per 10 s). That tail exists for the 1-page control as
  well, so it is the idle repaint loop under software GL, not layout. Not attributed further (no sampling profile was taken on the emulator).
- 360 dp vs 412 dp: no systematic difference beyond noise.

## 2. Native split (`spikes/p6-m3/layout_bench.rs`, release, `wordcraft_layout::layout`, bundled fonts only, 5 reps, i7-class desktop)

| view | pages | cold `LayoutCache` (shaping + pagination + passes) | warm cache (pagination + passes only) | shaping+paragraph share of cold |
|---|---|---|---|---|
| Print | 110 | 255.4 ms (252.7-313.7) | 38.3 ms (38.0-39.3) | 85.0 % |
| Web (360 px) | 1 | 233.5 ms (228.5-238.8) | 34.3 ms | 85.3 % |
| Read | 159 | 233.5 ms (226.0-242.0) | 35.5 ms | 84.8 % |

Docx parse: 38 ms. Warm Print layout includes the repeated total/footnote passes, so all passes together are about 38 ms (15 %).

- Shaping/paragraph building is **85 %**, pagination plus all repeated passes **15 %**. The plan's threshold for option (c) is "shaping >= 2/3".
- Web Layout is **not** cheaper (233 vs 255 ms, -9 %): the per-paragraph work dominates, not page totals. Option (b) as a speed fix is refuted. (Web Layout was
  measured with `web_width` 360 only; it shows one tall "page".)
- Native 255 ms vs the emulator's roughly 5-9 s long task gives a wasm-on-emulator slowdown of about 20-35x (consistent with the 17 s at 20x desktop throttle,
  once desktop wasm is 4x slower than native).

## 3. Recommendation (section 7 step 2)

1. **(a) always**: the shell shows "Opening <name>..." until `opened`; long cache headers for the wasm. The emulator spends 15-25 s before `opened` even for the
   control, so a grey page is the larger user-visible problem than the layout.
2. **(c) warm the cache in slices** as the document-specific fix: shaping is 85 % of the layout, so slicing it into 8-10 ms chunks removes the long task and leaves
   a ~40 ms (native) / ~1 s (emulator, ESTIMATE) pagination. It is the smaller patch (~100-200 lines in `crates/layout` + a call in the web app) and does not need the unproven
   resumable pagination of (d).
3. **Not (b)** (Web Layout is not cheaper) and **not (d)** unless (c) leaves a pagination task over 200 ms on the phone (pagination is only 15 %).

## 4. Not measured / caveats

- No phone; emulator under software GL is a bound, not a prediction (WP14).
- The emulator split into wasm compile vs parse vs layout was not taken (no `--profile` run); the 5 s layout figure is a difference of longest tasks from one clean pair.
- Phase 0's 240 s was not reproduced; this dist/engine opens in 25 s median. The cause of the old figure stays unproven (older build).
- The per-run harness JSON was printed to stdout and saved by `spikes/p6-m3/emu-runs.sh` into `E:/office-target/tmp`; the 12 files were copied after the fact (a crash mid-run did not lose any, but
  the script does not write into the repo itself).
- Native numbers are one desktop machine; wasm/native ratio taken from the Phase 4 desktop figures (1.0 s at 1x) vs 0.255 s native.
