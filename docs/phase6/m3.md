What the emulator numbers say:
- `opened` is **not** where the stall shows: the big file is +7 s at 412 dp and about equal at 360 dp versus the control, and the spread of the control
  alone (14-29 s) is larger than that difference. The emulator is slow and noisy for everything (the 1-page file has an 8 s long task too: wasm
  instantiation/first frame under swiftshader), so a 3-run median cannot resolve the document-specific cost from the page-load cost.
- The document-specific cost is the extra long task: longest task 9.5 s (412) / 8.5 s (360) for 108 pages vs 4.3 / 8.3 s for the control (412 dp pair is clean; 360 dp control was inflated by a first-run outlier).
  That puts the layout at roughly 5 s (ESTIMATE, difference of longest tasks, one clean pair) on the emulator.
- Phase 0's 240 s and the 20x-throttle desktop 51 s are not reproduced as one stall. What does occur is a long **tail**: 5 of 6 big runs and also 3 of 6 control runs keep
  producing long tasks (1-2 s each, every few seconds) for 35-220 s after `opened` (`busy_ms_by_10s` stays at 0.5-2 s per 10 s). That tail exists for the 1-page control as
  well, so it is the idle repaint loop under software GL, not layout. Not attributed further (no sampling profile was taken on the emulator).
- 360 dp vs 412 dp: no systematic difference beyond noise.

Docx parse: 38 ms. Warm Print layout includes the repeated total/footnote passes, so all passes together are about 38 ms (15 %).

- Shaping/paragraph building is **85 %**, pagination plus all repeated passes **15 %**. The plan's threshold for option (c) is "shaping >= 2/3".
- Web Layout is **not** cheaper (233 vs 255 ms, -9 %): the per-paragraph work dominates, not page totals. Option (b) as a speed fix is refuted. (Web Layout was
  measured with `web_width` 360 only; it shows one tall "page".)
- Native 255 ms vs the emulator's roughly 5-9 s long task gives a wasm-on-emulator slowdown of about 20-35x (consistent with the 17 s at 20x desktop throttle,
  once desktop wasm is 4x slower than native).

## 3. Recommendation (section 7 step 2)

1. **(a) always**: the shell shows "Opening <name>..." until `opened`; long cache headers for the wasm. The emulator spends 15-25 s before `opened` even for the
   control, so a grey page is the larger user-visible problem than the layout.
2. **(c) warm the cache in slices** as the document-specific fix: shaping is 85 % of the layout, so slicing it into 8-10 ms chunks removes the long task and leaves
   a ~40 ms (native) / ~1 s (emulator, ESTIMATE) pagination. It is the smaller patch (~100-200 lines in `crates/layout` + a call in the web app) and does not need the unproven
   resumable pagination of (d).
3. **Not (b)** (Web Layout is not cheaper) and **not (d)** unless (c) leaves a pagination task over 200 ms on the phone (pagination is only 15 %).

## 5. Step 2: the fix, (a) + (c) (2026-11-02, branch `p6-m3fix`)

### What changed
- **(a) Never a grey page** (our code). The shell already said "Opening Docs…" but only until `wordcraft:ready`; between `ready` and `opened`
  (3-10 s at 6x CPU, 15-25 s on the emulator) the status was empty and the iframe showed the editor's blank or frozen canvas. Now a cover
  (`#ed-cover`, `web/shell/shell.js` `cover()`) names the file ("Opening uz108-latn.docx…", new catalog row `ed.opening`, uz-Latn/uz-Cyrl/ru
  `reviewed:agent-opus:2026-11-02`) over the editor from the hand-over until `<prefix>:opened`, for the two editors that post `opened` (Docs, Slides);
  `failed` and the bridge timeout drop it. The docserver page (`services/docserver/static/editor.js`) already keeps its status until `opened`.
  **Cache headers needed no change:** `hoshiya-serve` already sends `public, max-age=31536000, immutable` for trunk-hashed files and `no-cache` for
  `index.html` (`services/suite-serve/src/lib.rs` `editor_headers`; checked with curl on this dist: the 45 MB wasm, `br`, immutable). The docserver mounts the same routes.
- **(c) Warm the cache in slices**, carried patch `wordcraft/0142`: `wordcraft_layout::warm` walks the body blocks in document order with the
  first pass's walk state (`pass_ctx`/`new_ctx`, split out of `layout_pass`) and lays each paragraph (`para_labelled`) and each table
  (`table::layout_table`, the call `place_table` makes) into the `LayoutCache` until the budget is spent; `Session::warm_layout` uses the options
  `Session::layout` uses (now one `layout_options`). Only `wordcraft-web` calls it: after a document arrives it runs one slice per frame, draws nothing
  meanwhile, and posts `wordcraft:opened` after the frame that shows the document. Desktop apps never call it.
- **Slice size 25 ms, not 8-10.** At 6x CPU a 9 ms slice left about 60 % of the warm-up to frame overhead (sweep, one build, uz108, 2 runs each:
  warm-up wall 6.5-6.8 s at 9 ms, 4.7-4.8 s at 25 ms, 4.3-4.9 s at 45 ms). 25 ms stays under the 50 ms long-task line.
- First build warmed top-level paragraphs only: 2,428 of 3,753 lookups still missed (the fixture's 48 tables hold 960 cell paragraphs), and the
  `opened` frame barely shrank. Tables are warmed through `layout_table` since; the pass then misses 508 (footnotes, headers, page-field paragraphs).

Done-check (plan section 7):
- **108-page `opened` ≤ 1.5x the 1-page `opened`: not met.** Idle: 12.0 s vs 1.5 x 6.6 s (median) = 9.9 s; loaded: 15.7 s vs 10.7 s. (c) does not remove
  work, it moves it into frames, and the frames cost overhead; `opened` is about equal (idle -0.5 s) to worse (loaded +1 s).
- **No main-thread task > 200 ms in the 10 s after `opened`: met in 5 of 6 after-runs** (81-149 ms), one loaded run 207 ms. It was already met before (55-150 ms).
- **The longest task drops by a third** (idle 6.2 → 3.9 s median, loaded 6.7 → 5.1 s), and the user sees the named cover instead of a grey page throughout.

### Why the 108-page open is still one 4-5 s task
Instrumented build (removed again): after the warm-up the `opened` frame's `WordApp::ui` took 3,463 ms, of which `Session::layout` 821 ms
(hits 3,245, misses 508, plus `next_first_line`, which lays out keep-with-next lookaheads without the cache). The other ~2.6 s is UI work that
grows with the document: a CPU profile of a names-kept build shows `chrome::status_bar` (`Session::selects_whole_story` → `Document::start_of`/`end_of`,
each collecting every paragraph path of the body on **every frame**, plus the first word count) and the ribbon's style gallery. So the remaining
first-frame cost is mostly not layout; slicing the layout further cannot reach the 1.5x target.

### Next steps (not done here; owner/plan decision)
1. `Document::start_of`/`end_of` without `para_paths` (stop at the first/last paragraph): removes a whole-document walk from every frame, which also
   matters for the idle cost of large documents (section 1's tail). Small upstream patch in `crates/doc`, no number allocated.
2. Word count off the first frame (computed in the warm-up slices or lazily).
3. If `opened` must reach 1.5x: option (d), first screen first.
