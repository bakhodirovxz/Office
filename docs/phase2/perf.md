# Phase 2 performance: the 108-page document

Status: **WP10a done (2026-10-20); N1 (headless native) measured; N2 (desktop GUI) and N3 (web) still to do (WP10).**
Machine: Windows 10, 12 cores, 11.8 GB RAM, Intel UHD 630, no discrete GPU. Release profile of the docs domain
(`opt-level 3`, thin LTO). Each figure is the median of 5 timed rounds after one warm-up round; every run was started alone
(no other build running). Commit: the WP4 commit on branch `phase-2` (see `git log`).

## The test documents (WP10a)
Generated by `scripts/translit/make-108.py` (raw OOXML, no dependencies, seeded, so the files are reproducible):

```
python scripts/translit/make-108.py --script latn --paras 49 --out domains/docs/crates/docs-translit/tests/fixtures/uz108-latn.docx
python scripts/translit/make-108.py --script cyrl --paras 47 --out domains/docs/crates/docs-translit/tests/fixtures/uz108-cyrl.docx
```

- **Synthetic.** Words come from the reviewed golden list (Latin or Cyrillic column), no corpus or personal data.
- **Content:** a title and a TOC field spanning 12 entries, 12 chapters with Heading 1/2, justified and left paragraphs, numbered
  lists, a 5x4 table every 11 paragraphs, a text box per chapter, a header with a PAGE field, a footer with PAGE and NUMPAGES
  complex fields, footnotes (79 and 64), hyperlinks (53 and 58), mid-word bold/italic run splits, a different font inside a word,
  and `ru-RU` / `en-US` tagged sentences (document default `uz-Latn-UZ` / `uz-Cyrl-UZ`).
- **Deviation from the plan:** the plan says Word COM. The files are not written by Word, so the realistic Word run splits
  (rsid, proofErr) are not present. Word was used only to **check the page count**: `Document.ComputeStatistics(wdStatisticPages)`
  gives **108 for both files** (latn `--paras 49`, cyrl `--paras 47`; found by trying `--paras` values in Word). R11 (no corpus) stands.
- **Engine page count:** 110 for both files (the engine's fonts and line breaking differ from Word's; both are recorded).
- **Size:** latn 139,902 B and cyrl 153,940 B on disk (compressed); text 331,813 B (Latin, 1 byte per letter) and 530,687 B
  (Cyrillic, 2 bytes per letter), i.e. about 0.33 M characters each. 2,050 / 2,011 paragraphs, 3,994 / 3,850 runs in all stories.

## WP10a: what the engine costs on these files (no command yet)
`cargo test --release -p docs-translit --test perf -- --ignored --nocapture --test-threads 1` (`engine_baseline_108`):

| Step | latn | cyrl |
|---|---|---|
| open `.docx` (parse) | 41-53 ms | 44-53 ms |
| first full layout / pagination (110 pages) | 276-312 ms | 314-335 ms |
| iterate all runs of all stories (read only) | 1.3-1.4 ms | 1.6 ms |
| `uz_translit::convert` of the whole text, one string | 37-46 ms | 27-31 ms |
| save `.docx` (serialise) | 21-26 ms | 30-38 ms |
| touch every body paragraph, then lay out again | 280-345 ms | 309-333 ms |

Raw rounds (latn): layout 276 / 312 / 298 ms; touch-all+relayout 280 / 345 / 290 ms. (cyrl): layout 316 / 335; relayout 309 / 333.

**What this says.**
- Iterating the runs is free (about 1 ms). The transliteration of the full text is 30-45 ms, about 8-11 MB/s through `convert` on
  this machine (the crate's own benchmark says 20-27 MB/s on a plain text; this text is dense with dictionary words and digraphs).
  The conversion is not the cost.
- **Layout is the cost.** A full relayout of 110 pages is about 0.3 s native (2.6-3 ms a page), 7 to 8 times the conversion. Any
  command that changes every paragraph pays it once, because the layout cache is keyed by each paragraph's `rev` and the command
  touches every paragraph (`para.rs:829`). Skipping unchanged paragraphs is already what the cache does; a document in which
  every paragraph changes cannot use it.
- **Projection for web (PROJECTION, not measured).** Phase 0 measured 16-22 ms a page in emulator wasm (4-page document, warm). Applied to
  110 pages that is 1.8-2.4 s of layout alone, i.e. **at or over the 2 s gate on an emulated phone**. Native here is 2.6-3 ms a page,
  so that emulator figure is 6 to 8 times native. Desktop Chromium wasm is usually 1.5 to 3 times native, which would be
  0.4 to 0.9 s. N3 must measure it; the risk R1 (emulator/web over 2 s) is **open** and is a layout cost, not ours.
- **Design consequence:** edits are batched by construction (one command, one `Session::run`, one undo checkpoint, one `touch`, every
  paragraph rewritten once). There is nothing more to batch: the single relayout is the floor. The only lever left is upstream's
  layout (parallel or incremental), which is a carried layout patch and the owner's call (plan WP10).

## N1: the command, headless native
`cargo test --release -p docs-translit --test perf -- --ignored --nocapture --test-threads 1` (`perf_108`). The session opens the
file and lays it out once (as the editor shows it), then the timer starts at `Session::run("tools.translitCyrl" | "tools.translitLatn")`
and stops when the new layout is finished (`Session::layout()`). Undo and redo are timed the same way.

| Direction (file) | pages before -> after | run() | of which ours (convert + apply) | relayout | **command -> finished layout** | undo -> layout | redo -> layout |
|---|---|---|---|---|---|---|---|
| to Cyrillic (latn) | 110 -> 114 | 59-67 ms | 58-65 ms (convert 53-59, apply 5-6) | 303-372 ms | **362-438 ms** | 36-49 ms | 38-47 ms |
| to Latin (cyrl) | 110 -> 106 | 47-52 ms | 46-47 ms (convert 41-48, apply 4-6) | 293-302 ms | **348-353 ms** | 39-42 ms | 40-42 ms |

- Rewritten per run: 1,990 paragraphs and 3,771 runs (to Cyrillic), 1,951 paragraphs and 3,652 runs (to Latin); the paragraphs that
  hold no letters (empty, numbers only) stay borrowed and keep their cached layout.
- Raw runs, to Cyrillic (command -> layout): 362, 438, 385 ms; to Latin: 357, 348, 353 ms (three full processes for the first,
  two to three for the second; the first batch of this table ran both tests in parallel and read 404 ms / 357 ms, which is why the
  runs above use `--test-threads 1`).
- **Our part (convert + apply) is 46-65 ms, under the 100 ms the plan sets** before blaming layout. The rest is the engine's layout.
- Undo and redo are 36-49 ms: the engine restores the previous `Arc` snapshot, whose paragraph revisions are cached.
- The page count moves with the script (Cyrillic letters are wider): 110 -> 114 to Cyrillic, 110 -> 106 to Latin. Reported, not a defect.

## Gate reading so far
- **N1 (headless native): 0.35 to 0.44 s from command to finished layout for 108 (engine: 110) pages, against the 2 s gate.** ONLYOFFICE plugin: 62 s.
- N2 (desktop GUI) and N3 (web, Chromium) are not measured yet. N2 should add the frame time (egui paint, tens of ms). N3 is the risk
  (wasm layout, see the projection above).
- Docs CLI wall time on the same files: see the last section.

## Docs CLI, release (`docs-cli`, wall time of the whole process)
`docs-cli commands --json` lists `tools.translitCyrl`, `tools.translitLatn` and `tools.translitAuto` (proves the install hook in the CLI).
Process wall times, three runs each, release build of the docs domain, files from `tests/fixtures`:

| Command | Wall time |
|---|---|
| `docs-cli info uz108-latn.docx` (open + full layout + JSON; `layoutMs` 362 ms, 110 pages) | 458, 451, 461 ms |
| `docs-cli run --file uz108-latn.docx --cmd 'tools.translitCyrl={}' --save out.docx` (open, command, save, no layout) | 198, 196, 192 ms |
| `docs-cli run --file uz108-cyrl.docx --cmd 'tools.translitLatn={}' --save out.docx` | 168, 186, 193 ms |
| `docs-cli info out-cyrl.docx` (the converted file: 114 pages, `layoutMs` 345 ms) | one run |

`run` does not lay the document out, so it is the cheap path (about 0.2 s for 108 pages, process start included); the editor pays the layout
(N1 above). `docs-cli run ... --print` shows the result JSON: `{"direction":"cyrl","paragraphs":1990,"runs":3771,"skipped":{"field":0,"lang":0,"locked":0},"ms":{"convert":53.5,"apply":4.8}}`.

## WP5 Sheets and WP6 Slides: the commands, headless native (engine level)
Commands `tools.translitCyrl|Latn|Auto` in `gridcraft-engine` (`cmd/translit.rs`, patch `gridcraft/0120`) and `deckcraft-engine`
(`cmd/translit.rs`, patch `deckcraft/0120`). Release builds, `Session::execute` timed from the call to its return; the document is
generated in memory (`tests/translit.rs`, `timing_on_a_large_sheet` and `timing_on_a_large_deck`, `#[ignore]`):
`cargo test --release -p gridcraft-engine --test translit -- --ignored --nocapture`, the same for `-p deckcraft-engine`.

| Document | Converted | `execute()` total | of which scan + convert | of which apply (+ recalc and row heights) | undo |
|---|---|---|---|---|---|
| sheet 50,000 rows x 5 columns (4 text, 1 number) | 200,000 cells | 1,072 ms | 495 ms | 573 ms | 2.1 ms |
| sheet 200,000 rows x 5 columns | 800,000 cells | 3,703 ms | 1,774 ms | 1,917 ms | 5.3 ms |
| deck 100 slides (8 shapes of 2 paragraphs, plus notes) | 1,700 paragraphs | 16 ms | 16 ms | 0.2 ms | 0.03 ms |
| deck 500 slides | 8,500 paragraphs | 76 ms | 75 ms | 0.3 ms | 0.01 ms |

- Sheets scales linearly at about 4.6 microseconds a cell (2.2 scan and convert, 2.4 apply). The apply side is `edit()`: one workbook
  copy-on-write, one incremental recalculation of the formulas that read a changed cell, and `auto_row_height` for the changed rows. A
  realistic HRM sheet (a few thousand cells) is under 50 ms. Undo is a snapshot swap.
- Slides has no layout in the measurement, so it reads the conversion alone: 9 microseconds a paragraph, a 500-slide deck in 76 ms.
  The cost in the editor is the repaint of the visible slide, not the command.
- Neither has an N2/N3 figure (desktop frame, wasm). The sheets clock is `SystemTime`, 0 on wasm (it has none); the `ms` field is then 0.
