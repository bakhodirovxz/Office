## 2. Per-app mechanisms and the minimal carried hook

Common to all apps: the catalogs are **files in the overlay** (`$OFFICE_OVERLAY_DIR/catalog-<code>.tsv`). The generated module turns them into `const` strings (`include_str!` with an absolute path; brand.md §3.2), so no catalog byte ever enters `patches/` or the upstream tree. Each app gets one patch, `0110-<app>-office-languages`, whose new entries sit under `#[cfg(office_uz)]` (I8).

### 2.1 wordcraft (TSV)

- **How a catalog is loaded.** `LANGUAGES: [LangInfo; 23]` (`crates/ui-egui/src/i18n/mod.rs:55-167`). Each entry has `source: &'static str` (`include_str!("xx.tsv")`) and a `OnceLock<Catalog>` parsed on first use (`:168-180`, `Catalog::parse` in `catalog.rs`). Format: `context<TAB>English<TAB>translation`, escapes `\n \t \\`, `{name}` placeholders, a trailing `…` must match (`ru.tsv:1-14`). Contexts: `preview`, `template` (`catalog.rs:26`).
- **Lookup.** `tl!` → `t` → `tr(current(), s)` (`mod.rs:359`, `:398-403`); `tc`/`trc` for contexts (`:365`, `:370`). Missing → English (`unwrap_or(s)`).
- **How the switch is reached.** File › Options › General › "Interface language" (`options.rs:421` section, `:616-630` combobox with "Auto"). Command `ui.language` (`lib.rs:1415`; allowed list `:2389`). Setting `UiState.language: String` (`lib.rs:266`), resolved by `Lang::from_pref` (`mod.rs:250`). Auto: `system_lang()` (`mod.rs:307`, `detect_system_lang` `:316`; env `WORDCRAFT_LANGUAGE`, then `sys_locale::get_locales()`, browser on web through the `js` feature).
- **Hook 0110** (estimated about 15 changed upstream lines):
  ```rust
  pub static LANGUAGES: [LangInfo; 23 + crate::office_overlay::EXTRA_LANGS] = [
      /* the 23 upstream entries, unchanged */
      #[cfg(office_uz)] LangInfo { code: "uz-latn", name: "Oʻzbekcha", source: crate::office_overlay::CATALOG_UZ_LATN, prefer_hans: false, editing_lang: None, catalog: OnceLock::new() },
      #[cfg(office_uz)] LangInfo { code: "uz-cyrl", name: "Ўзбекча",   source: crate::office_overlay::CATALOG_UZ_CYRL, prefer_hans: false, editing_lang: None, catalog: OnceLock::new() },
  ];
  ```
  and, in `candidates()` (`mod.rs:274-290`), after the `zh` rule:
  ```rust
  if primary == "uz" && !parts.iter().any(|p| matches!(*p, "latn" | "cyrl")) {
      let cyrl = tag.to_ascii_lowercase().contains("@cyrillic");          // I6: before '@' is stripped
      out.insert(out.len().saturating_sub(1), if cyrl { "uz-cyrl" } else { "uz-latn" }.into());
  }
  ```
  `editing_lang: None`, because `wordcraft-proof` has no Uzbek dictionary (Phase 2 may add a Hunspell `uz` dictionary).
- **Plural forms.** None. The upstream convention is count-neutral wording (`ru.tsv:14`, "Слов: 21"). Uzbek suits this naturally, since a noun after a numeral stays singular ("5 ta fayl"). `DRAFTING.md` forbids plural-dependent wording.
- **Is `uz` accepted?** As a **system locale**, yes, after the hook: `uz`, `uz-UZ` and `uz_UZ.UTF-8` map to uz-latn; `uz-Cyrl-UZ` and `uz_UZ@cyrillic` map to uz-cyrl. As a **setting or command value**, `Lang::from_code` matches exact codes only (`mod.rs:244-246`), so `ui.language {"language":"uz"}` is rejected and the setting is kept. That is acceptable: the picker writes the full code. Codes are lowercase by upstream rule (`tests.rs:121`).
- **Tests the hook must satisfy with the overlay active.** `bundled_catalogs_are_well_formed` (`tests.rs:117-131`: no parse errors, placeholders match, no stray whitespace, no `...`, **>700 entries**); `every_tab_and_command_is_translated` (`:136-155`); `polish_covers_every_key_of_every_other_catalog` (`:986-1000`: our uz keys must be a subset of `pl.tsv`'s keys, unless uz is added to its exclusion list. **Constraint for extraction: P1 keys come from the key universe that `pl.tsv` covers**; pl has 2,585 of 2,616). Our own `uz_latn_covers_p1`/`uz_cyrl_covers_p1` live in `office_overlay_tests.rs`.

### 2.2 gridcraft (Rust match tables)

- **How a catalog is loaded.** Compiled in: `enum Language` (`crates/ui-egui/src/i18n.rs:24-36`), `ALL: [Self; 11]` (`:39`), `name()` (`:44-58`), `code()` (`:61-75`), `from_tag()` (`:81-96`; it matches the **primary subtag only**), `system()` (`:100-110`; `sys_locale` on desktop, `navigator.language` on web), `tr()` (`:119-132`) dispatching to `xx::translate(&str) -> Option<&'static str>` (`i18n/ru.rs:3-…`) or the `JAPANESE` slice (`:178`). Fallback: English after the `context|` prefix (`:131`). Current language: egui context data (`current` `:167`, `set_current` `:172`).
- **How the switch is reached.** View tab › "Interface language" (`ribbon.rs:2225-2236`); Backstage › Options (`backstage.rs:949-953`); command `app.language.set` (`lib.rs:626-636`, alias `code`); setting `UiState.language` (`lib.rs:73`), saved in `ui.json` with serde `rename_all = "lowercase"` (`i18n.rs:22`); web follows the browser except CJK (`apps/gridcraft-web/src/web.rs:52-61`).
- **Hook 0110** (estimated about 25 changed upstream lines). Variants `#[cfg(office_uz)] #[serde(rename = "uz-latn")] UzLatn` and `… "uz-cyrl" UzCyrl`; `ALL: [Self; 11 + office_overlay::EXTRA_LANGS]`; one `#[cfg]` arm each in `name`, `code`, `tr`; in `from_tag` an early `"uz"` branch that picks Cyrillic when the lowercased tag contains `cyrl` or `@cyrillic`. The translation functions come from the overlay: `build_office.rs` (brand.md §3.4) reads `catalog-uz-*.tsv` and **generates** `fn translate_uz_latn(text: &str) -> Option<&'static str> { Some(match text { "Paste" => "…", … _ => return None }) }` into `OUT_DIR`. That has the same performance and shape as upstream's tables, and no Rust source is ever exported from our tree.
- **Plural forms.** None (`"{n} days ago"` style, `ru.rs:355-359`).
- **Is `uz` accepted?** Yes everywhere after the hook, because `from_tag` already takes primary subtags: `parse("uz")` gives UzLatn, `parse("uz-cyrl")` gives UzCyrl, and `app.language.set {"language":"uz"}` works. The existing test `language_commands_switch_and_persist` (`i18n.rs:700-712`) iterates `ALL`, so it exercises our serde names honestly.
- **Not touched.** `formula_locale` (`i18n.rs:112-114`: En/Es function names only). Localised function names and argument separators are outside Phase 1 (WP10).

### 2.3 pdfcraft (TSV with contexts and plurals)

- **How a catalog is loaded.** `LANGUAGES: [LangInfo; 23]` (`crates/ui-egui/src/i18n/mod.rs:150-213`), fields `code, name, source, plural: fn(u64) -> usize, rtl` (`:37-50`). The catalog is parsed with the language's plural-form count (`:217-233`). Format (`ja.tsv:1-16`): `context` empty, `@id` (command id), `@plural` (source `one|other`, translation lists the language's forms with `|`), or a free context for `tr_ctx`. Lookup: `tl!` (`lib.rs:17-21`) → `t` (`mod.rs:427-430`) → `tr` (`:438-440`); `tr_ctx` (`:454`), `tr_id` (`:459`), `trn` (`:553`), `key_name` (`:433`).
- **How the switch is reached.** Preferences › "Interface language" (`js_ui.rs:265-282`), with immediate relabel (`:278-281`); setting `PdfCraftApp.language` (`lib.rs:541`, default `auto` `:918`). Auto on desktop: env `LC_ALL`/`LC_MESSAGES`/`LANG`, macOS `defaults`, Windows `sys_locale::get_locales()` (`mod.rs:345-391`); **web: English always** (`:394-397`, I3).
- **Hook 0110** (estimated about 30 changed upstream lines, plus a new engine `build.rs`):
  - two `#[cfg(office_uz)]` `LangInfo` entries with `plural: plural_one_other` (`mod.rs:53`) and `rtl: false`;
  - the `candidates()` rule as in wordcraft (`mod.rs:302-327`);
  - `DATE_LANGUAGES: [DateLanguage; 23 + EXTRA]` (`crates/engine/src/dates.rs:59`) with two `#[cfg(office_uz)]` entries taken from a **new** `crates/engine/build.rs`. That file reads `$OFFICE_OVERLAY_DIR/dates-uz-{latn,cyrl}.tsv` (12 months, 12 short months, 7 days, 7 short days; `months_with_day: None`, because Uzbek does not inflect the month after a day number: "8-oktabr") and writes `office_dates.rs` into `OUT_DIR`. Cargo picks up a `build.rs` at the crate root without a `Cargo.toml` edit. The engine is below ui-egui, so it gets its own reader (`xtask layers`, brand.md §3.4);
  - P2 (I3): `sys-locale = { version = "0.3", features = ["js"] }` in `crates/ui-egui/Cargo.toml:64`, and the wasm `detect_system_lang` uses `sys_locale::get_locales()` like the Windows path. The lockfile is unchanged (the `js` feature's crates are already in it).
- **Plural forms.** `@plural` rows: CLDR gives Uzbek `one` (n = 1) and `other`, hence `plural_one_other`. Uzbek drafts normally repeat the same text in both forms ("{n} ta sahifa|{n} ta sahifa"). Lint checks the form count equals 2.
- **Is `uz` accepted?** System tags: yes, as in wordcraft. Preference values: exact codes only (`Lang::from_code` `mod.rs:261`, `from_pref` `:267`).
- **Tests to satisfy with the overlay active.** `bulk_field_properties_labels_are_in_every_full_catalog` (`mod.rs:826-…`), `signature_appearance_labels_are_in_every_catalog` (`:948-…`, it iterates languages with a non-empty `source`), `date_languages_are_the_interface_languages` (`:3347-3353`), the command-label placeholder/ellipsis check (`:3330-3345`), `object_ui.rs:418`, `sign_ui.rs:1537`, `icons.rs:82`. All of them skip empty catalogs, so pristine-like builds pass. With the overlay active, their key sets are P1 (§5.3).
- **In-tree vs overlay.** In-tree catalogs would need `ATTRIBUTION.toml` SHA-256 rows (`xtask/src/assets.rs:243-260`; all 22 TSVs are listed). The overlay keeps that gate green.

### 2.5 deckcraft: the minimal mechanism (0110 + 0111)

deckcraft has no i18n at all: all strings are English literals, there is no `sys-locale` dependency, and `ui-egui` has no `web-sys` (`crates/ui-egui/Cargo.toml`). This design goes into `docs/phase1/deckcraft-i18n.md` in WP9d, unchanged.

**Options.**
- (a) Fluent or gettext: new dependencies (lockfile, cargo-deny) and a second catalog format for the reviewers. Rejected.
- (b) Copy wordcraft's model: English-key TSV, `t(&str) -> &str`, `OnceLock` catalogs, thread-local current language. No dependency, and the same format as two other apps, so the exporter, lint and reviewers are shared.
- (c) Wrap at every call site. About 1,400 hunks in hot files. Rejected.

**Choice: (b), wrapped at the helper choke points**, so the patch is small and coverage grows with the catalog alone.

**0110-deckcraft-i18n-mechanism** (all new logic in new files):
- `crates/ui-egui/src/i18n.rs` (new, about 220 lines with tests): a `LANGUAGES` slice built from the overlay (`en` built in, then `ru`, `uz-latn`, `uz-cyrl` when their `CATALOG_*` constants are non-empty); a parser identical in grammar to wordcraft's `catalog.rs` (escapes, placeholders, `…` rule; strict parse, bad lines skipped and logged); `t()`, which calls `office_overlay::rebrand` on the result (brand.md §3.3); `fmt()`; `set_current`/`current` (thread-local, so parallel kittest harnesses stay independent); `from_pref`; `normalize_pref`, which accepts `uz` as an alias for `uz-latn`.
- `crates/ui-egui/src/lib.rs`: `mod i18n;` plus a `tl!` macro (4 lines); `UiState` (`lib.rs:239`) gets `#[serde(default = "auto")] pub language: String`, so old `ui.json` files still load (`settings.rs:20-34` already tolerates unknown or missing fields through the defaults); one line at the start of the frame, `i18n::set_current(i18n::from_pref(&self.ui.language))`; one row in `UI_COMMANDS` (`lib.rs:359`), `("app.language.set", "Interface Language", None, "{language}")`, plus its handler (about 8 lines).
- `crates/ui-egui/src/backstage.rs`: an "Interface language" combobox on the Options page (`Nav::Options`, `:267`), about 12 lines.
- **Auto** resolves to `office_overlay::DEFAULT_LANGUAGE` when that is a concrete code, otherwise to `en`. No system detection in Phase 1: adding `sys-locale` changes deckcraft's lockfile and deny surface. It is already in the other three locks, so Phase 2 can add it at low cost. This is the honest gap at the gate: deckcraft follows the language the user picks, not the OS.

**0111-deckcraft-i18n-p1-strings** (display-site wraps, not label changes):
- **Helpers**: `big()` (`ribbon.rs:253`), `small()` (`ribbon.rs:288`), `tip()` (`ribbon.rs:304`) translate their `label` argument. This covers about 470 ribbon literals and the command labels shown as tooltips.
- **Menus**: the menu builder in `menus.rs` (the `(label, id)` tables, e.g. `:292`) translates at draw time. The command palette translates `CommandInfo.label` (`crates/engine/src/cmd/mod.rs:63`) at display, so the engine stays untouched.
- **Backstage nav labels** (`backstage.rs:112` match) and the page headers.
- **Explicit `tl!`** on the P1 literals in the About dialog, the common buttons (OK, Cancel, Close, Apply) and the File › Open/Save/Export pages. About 60 call sites.
- Everything else stays English until a later phase wraps it. **The catalog can already hold any string that reaches a helper.**
- **Plural**: none. `DRAFTING.md` requires count-neutral wording ("Slaydlar: 5").
- **ru for deckcraft**: drafted by the agent like uz, status `draft`. Who reviews ru is an owner decision (O4).
- **Carry risk**: `ribbon.rs` (3,619 lines) and `backstage.rs` (1,382 lines) are hot, but the 0111 hunks are 3 helper bodies plus about 60 one-token wraps. WP14 measures it.

## 4. Canonical catalogs in our tree

### 4.1 Layout

```
i18n/
  config.toml          locales, fallback chains (§5), batch size, length-ratio limit, app list, upstream TSV paths
  glossary.tsv         batch 0: core terms (≈150), owner-reviewed first
  shared.tsv           scope "*": English strings used by 2+ apps (670 at the old BASE), one review exported to all
  wordcraft.tsv  gridcraft.tsv  pdfcraft.tsv  deckcraft.tsv     scope = app: app-only strings and app overrides
  DRAFTING.md          rules for draft producers
  review/batch-NN.csv  review/batch-NN.returned.csv  review/LOG.md
```

### 4.2 Row format

UTF-8, LF, no BOM, a header line, sorted by `id`, cells escaped like the upstream TSVs (`\n \t \\`), so a native export is a column projection:

```
id  context  source_en  uz_latn  uz_latn_status  uz_cyrl  uz_cyrl_status  ru  ru_status  priority  apps  where  note
```

- `id`: the first 12 hex digits of SHA-1 over `scope \x1f context \x1f source_en`. It is stable while the English stays the same; a changed English string gets a new id (§6.3).
- `context`: upstream's own context verbatim. Empty, `preview`/`template` (wordcraft), `@id`/`@plural`/free contexts (pdfcraft), the `ctx|` prefix (gridcraft, stored split: context=`ctx`, source=`label`). Ours: `date.month.1`…`date.dayShort.7` for pdfcraft's engine dates (exported to `dates-*.tsv`, not the UI catalog).
- `*_status`: `state[:who[:date]]` with state `todo | draft | reviewed | rejected | obsolete`. Examples: `draft:agent-sonnet:2026-10-18`, `reviewed:owner:2026-10-21`. **Only `reviewed:owner:*` is trusted.** `ru` exists for overrides only (empty unless we change an upstream ru string) and for deckcraft, which has no upstream ru.
- `priority`: `P1 | P2`. `apps`: the comma list of apps that use the string (shared rows). `where`: one representative `path:line` in the patched tree, for reviewer context. `note`: free text (the draft rationale, reviewer comments carried from import).
- `@plural` rows hold the forms separated by `|` in each locale cell (Uzbek: 2 forms).

### 4.3 Rules that tie catalogs to branding and fonts

- Upstream-token preservation (I5): when `source_en` contains a `[apps.*].upstream_names` token or `ArtCraft`, every translation must contain the same tokens, the same number of times. "Part of … ArtCraft" sentences get no translation at all, because `rebrand` drops them.
- No working name (brand.md Rule W) in any cell.
- Every character of every uz cell must be drawable by the fallback font plus the app's UI faces (font.md §2). Lint checks the cmap.

## 5. Fallback chain

**Mechanism: merge at export time, not at run time.** Every upstream mechanism has exactly one fallback: English, the key (wordcraft `mod.rs:375,403`; gridcraft `i18n.rs:131`; pdfcraft `mod.rs:439`). Changing that would put logic into hot upstream files. Instead `i18n export` fills a locale's missing rows from the next locale in its chain, so the app sees a complete-looking catalog and its own `unwrap_or(English)` handles the remainder. The cost is zero runtime code and zero hook lines. In release mode a chain step only uses **trusted** rows of the earlier locale (reviewed Uzbek), or upstream's shipped ru.

**The question: `uz-Cyrl → uz-Latn → ru → en`?** Considered and rejected for the run time:
- **uz-Cyrl → uz-Latn (mixed script):** rejected. A user who picked Cyrillic sees Latin Uzbek words in the same toolbar, which reads as broken spelling rather than a fallback. And the step is never needed in practice: every uz-Cyrl draft is *derived* from uz-Latn (§6.4), so a reviewed uz-Latn row is reviewed again in Cyrillic in the spelling pass, and the two scripts reach coverage together.
- **No runtime transliteration** Latn↔Cyrl either: it is not reversible or safe without review ("ts"/"s" for ц, "ye"/"e" for е, the soft and hard signs, Russian loanwords "sentabr"/"сентябрь", "kompyuter"/"компьютер"), so it may only produce *drafts*.

**Recommended chains** (`i18n/config.toml`; owner decision O1):

| Locale | Chain | Why |
|---|---|---|
| `uz-Cyrl` | `uz-Cyrl → ru → en` | Same script on screen. Readers of Cyrillic Uzbek are, in practice, readers of Russian (ASSUMPTION, owner to confirm). Upstream ru is near-complete in wordcraft (2,571 / 2,616) and pdfcraft (2,314 / 2,670), but gridcraft has only 398 / 970 and deckcraft none, so en remains the last step. |
| `uz-Latn` | `uz-Latn → en` | Same script on screen, and upstream's behaviour. A fallback hit means a P2 string that is not translated yet, usually a technical one, where English is the source of truth. If the owner prefers `uz-Latn → ru → en` (HRM staff often read Russian better than English), it is a one-line config change. |
| `ru` | upstream ru → `en` | Unchanged (our `ru` overrides only). |
| `en` | source | — |

Effect on upstream tests: a chain-filled uz-Cyrl row counts as "translated" for `has()` (wordcraft `tests.rs:136`), which matches that test's intent ("never fall back to English"). uz-Latn cannot be filled from en (an English copy is not a translation, and it would game `entries.len() > 700`), so uz-Latn passes those tests only through real P1 coverage (I1). **The exporter never writes English text into a uz column.**

## 6. Tooling (WP9b: `crates/office-i18n` + `cargo xt i18n …`)

### 6.1 `i18n extract <app>|all`

Builds the key universe from the **patched** tree at BASE and merges it into `i18n/*.tsv`:
- wordcraft: the union of `(context, English)` over `crates/ui-egui/src/i18n/*.tsv`, plus a source scan for literals of `tl!`/`t(`/`tc(`/`fmt(t(` and `CommandSpec::new(id, label, location, …)` labels and location segments, plus `ribbon::TABS`. Keys found in source but in no catalog are reported as "new upstream strings".
- pdfcraft: the union over its TSVs (all contexts, `@plural` kept as `one|other`), plus the `COMMANDS` labels (`crates/engine/src/commands.rs`), plus the same `tl!` literal scan upstream's own test performs (`mod.rs:825`), plus the `DATE_LANGUAGES` English names (`dates.rs:59-…`) as `date.*` rows.
- gridcraft: the match-arm keys of `i18n/*.rs` and the `JAPANESE` tuples (`i18n.rs:178`), plus `tr("…")`/`lang.tr("…")` literal sites.
- deckcraft: the `tl!`/`t(` literals and the helper arguments (`big`/`small`/`tip`/menu tables) after 0111, plus the `cmd!` labels. Before 0111, the heuristic scan in report-only mode.
- `--test-required`: the key sets that upstream tests demand for any non-English catalog (wordcraft `tests.rs:136`; pdfcraft `mod.rs:826`, `:948`, `object_ui.rs:418`, `sign_ui.rs:1537`, `icons.rs:82`). They are computed by running those tests once against an **empty** uz overlay catalog and parsing their "missing"/"lacks" output. This gives an exact list without re-implementing the tests. It is the only extraction step that builds, and it runs under the build lock.
- Placement: a key used by two or more apps with identical context and English goes to `shared.tsv`; otherwise to the app file. Placement is stable: once a row exists, extract never moves it.
- wordcraft constraint (§2.1): P1 keys must be in `pl.tsv`'s key set, or the `polish_covers_every_key…` test fails.

### 6.2 `i18n lint` (errors fail CI job `i18n`; warnings are reported)

Errors:
- placeholders (`{name}`, `{}`, `{0}`, `%s`, pdfcraft `@id` targets) must equal the English set;
- the `…` rule, and three dots `...` forbidden (wordcraft `tests.rs:127`);
- `\n` count equal (multi-line ribbon labels "Community\nDiscord");
- no leading or trailing whitespace;
- `@plural` form count = 2 for uz;
- **apostrophes in uz-Latn**: oʻ/gʻ must use U+02BB, and the tutuq belgisi must be U+02BC. ASCII `'`, `‘` U+2018, `’` U+2019 and `` ` `` adjacent to a Latin letter are errors (the lint shows the fixed form);
- **script purity**: Cyrillic letters in a uz-Latn cell, or Latin letters in a uz-Cyrl cell outside placeholders, upstream tokens and allowlisted Latin terms (PDF, URL, MCP, product names);
- upstream-token preservation (§4.3); no working name (Rule W);
- glyph coverage: every character in a uz cell exists in the fallback font cmap or the app's primary UI face (font.md);
- duplicate `(scope, context, source_en)`; unknown context for the target app.

Warnings: the length ratio is above 1.6× English for ribbon and tab labels (from `where` paths in `ribbon.rs`/`backstage.rs`); a draft does not use the reviewed glossary term for a glossary source word; Latin-script `x`/`h` confusions (`xat`/`hat`) are flagged when the word is in the glossary.

### 6.3 Re-extraction after an upstream sync

- A new key becomes `todo`. A key that disappeared becomes `obsolete` (kept for history, never exported).
- Changed English means a new id. If an obsolete row's English is within 20% edit distance, its translations are copied into the new row as `draft:carried:<date>` with `note: carried from <old id>; English changed: "<old>" → "<new>"`. **A carried row is never `reviewed`**: the owner sees it in the next batch.
- Counts go to `i18n coverage` and STATUS.

### 6.4 Drafting (WP9e)

- **Batch 0 first**: `glossary.tsv` (about 150 terms: ribbon tab names, File/Edit/View/Insert/Format, Save/Open/Export/Print, cell/row/column/sheet, slide/layout/theme, page/annotation/signature, units, plus the date names for pdfcraft) and the brand.toml names and attribution drafts (brand.md §2 rule 6). **No catalog drafting starts until batch 0 has returned** (lever: every later draft follows the reviewed terms).
- Drafts: a sonnet builder, following `DRAFTING.md`. The rules:
  - follow the glossary;
  - official orthography (the 1995 Latin-script spelling rules): U+02BB for oʻ gʻ, U+02BC for the tutuq belgisi;
  - keep placeholders, `…`, `\n`, upstream tokens;
  - count-neutral wording;
  - at most 1.6× English length for labels;
  - **clean room**: never consult or copy Microsoft, ONLYOFFICE or LibreOffice localisations (general Uzbek computing vocabulary is fine);
  - one row at a time from the English meaning and the `where` context.
- Every draft row is `draft:agent-<model>:<date>` with a `note` when a term choice was uncertain.
- uz-Cyrl drafts come **from the uz-Latn draft** through `scripts/i18n/latn2cyrl-draft.py` (deterministic, labelled "draft aid, not uz-translit"; Phase 2 builds the real `uz-translit`). Rows with known-ambiguous letters (`e` at word start, `ts`, `yo/yu/ya`, loanwords) get `note: translit-ambiguous` so the spelling pass looks at them first.
- ru drafts: deckcraft only (no upstream ru).

### 6.5 Review batches and import (WP9f)

- `i18n review-export --batch N [--pass meaning|spelling]` writes `i18n/review/batch-NN.csv`. UTF-8 **with BOM** (Excel), at most **400 rows**, ordered glossary, then shared P1, then per-app P1 (wordcraft, gridcraft, pdfcraft, deckcraft), then P2. Columns:
  ```
  id, app, where, English, uz-Latn draft, uz-Cyrl draft, verdict (OK/FIX/REJECT), corrected uz-Latn, corrected uz-Cyrl, comment, en_hash
  ```
  - **Pass A, meaning**: uz-Latn. The uz-Cyrl column is shown read-only for context.
  - **Pass B, spelling**: uz-Cyrl, only for rows whose uz-Latn is already `reviewed`, freshly re-derived from the reviewed Latin text.
  - A batch file names the BASE and the export date in its first row (a `#` comment row that Excel shows as a header).
- `i18n review-import <file>`:
  - `en_hash` mismatch (English changed since export): the row is skipped and listed as stale; it reappears in the next batch.
  - `OK`: `reviewed:owner:<date>`.
  - `FIX` with corrected text: the owner's text replaces the draft and becomes `reviewed:owner:<date>`, **unless it fails lint**. Then it becomes `draft:owner-fix:<date>` with the lint message in `note`, and returns in the next batch for confirmation. **No tool ever alters owner text silently** (not even an apostrophe fix).
  - `REJECT` or a comment without a correction: `rejected`. It is re-drafted with the comment as input and returns in the next batch.
  - An empty verdict leaves the row unchanged.
- Every import appends to `review/LOG.md`: the batch, the counts per verdict, the stale rows. The returned CSV is committed next to the export, as evidence. It holds UI strings only, no personal data.
- Owner-facing hand-off text (Uzbek) is written by the agent that exports a batch. It states the pass, the row count and the estimated time.

### 6.6 Export to the overlay

`i18n export <app> --mode review|release` writes the native files into `$OFFICE_OVERLAY_ROOT/<app>/`:
- wordcraft, pdfcraft, deckcraft: 3-column TSV with upstream's header comment (clean-room note included), contexts verbatim, `@plural` forms joined by `|`;
- gridcraft: 2-column TSV (`ctx|label`, translation) that `build_office.rs` compiles to a `match`;
- pdfcraft: also `dates-uz-latn.tsv` and `dates-uz-cyrl.tsv` from the `date.*` rows (all 38 must be present, or the export fails, because the engine table needs complete arrays);
- `release`: only `reviewed:owner` rows, plus the chain fill (§5) from trusted sources. `review`: also `draft` rows. Rejected and obsolete rows are never exported;
- the export writes `catalog-meta.env` (`MODE=review`, `UZ_LATN_REVIEWED=N`, `UZ_LATN_DRAFT=M`, …). In review mode, the About dialog shows "Uzbek interface: DRAFT translation (N of M strings reviewed)" (a 3-line addition to `office_overlay.rs`). Every Phase 1 evidence screenshot therefore carries the draft label, and **no screenshot can present unreviewed Uzbek as final**.

### 6.7 `i18n coverage`

Prints, per app × locale: `keys K, P1 K1, todo T, draft D, reviewed R (R/K1 % of P1)`. CI job `i18n` fails if P1 drafts are below 100% for uz-Latn once WP9e is done. The gate report quotes these numbers.

## 7. Owner decisions

- **O1** Fallback chains (§5). Recommended: `uz-Cyrl → ru → en`; `uz-Latn → en`. This differs from PLAN §4.1, which said "uz never falls back to ru". The difference is the same-script argument for Cyrillic.
- **O2** Default language when the OS language is not supported: `en` (upstream) or `uz-Latn` (`brand.toml [i18n].default`). Recommended: `auto` (that is, en) until the P1 Uzbek strings are reviewed, then `uz-Latn` for HRM deployments.
- **O3** Language self-names in the pickers: "Oʻzbekcha" / "Ўзбекча" (proposed; batch 0).
- **O4** Who reviews deckcraft's ru drafts (the owner, or a Russian-speaking colleague of the owner).

## 8. Risks

- **Owner latency** (the largest). Mitigation: glossary first, P1 only, batches of at most 400, two short passes. The gate evidence is explicitly "draft" (§6.6).
- **I1 test pressure.** If wordcraft's 780 P1 rows are not reviewed by the gate, the overlay-active run quarantines two tests under class `i18n-incomplete`, with a count that must shrink. Pristine-like CI stays green.
- **Hot-file conflicts** in the language tables: each hook adds entries at the end of a table and one rule in `candidates`. Expected to be trivial on rebase; WP14 measures it.
- **Generated `match` size** (gridcraft): 970 arms per locale compile like upstream's own tables. No risk expected, but WP9c measures the build time.
- **Heuristic count** for deckcraft (§1). Replaced by the exact `extract` count after 0111.
